# ADDIS EATS — Rendering Strategy

| Route | Strategy | Why |
|---|---|---|
| `/` | Static rendering | The home page is shared content and does not depend on request-specific data. |
| `/menu` | Static rendering with ISR (`revalidate = 60`) | The menu data can be cached and refreshed periodically without rendering for every request. |
| `/menu/[id]` | Static generation with `generateStaticParams` | Dish IDs and details are known at build time, so each dish page can be generated ahead of time. |
| `/cart` | Static route shell with client-side state | Cart items are browser-specific localStorage data and are read after hydration in the client. |
| `/checkout` | Dynamic rendering (`force-dynamic`) | The page reads the request cookie `checkout-session` via `cookies()`, so it must be rendered per request. |

## Streaming and nested layout

- `app/menu/layout.js` renders the sidebar outside the menu page content.
- `app/menu/page.js` places the asynchronous `DishList` behind `<Suspense>`, allowing the menu shell and sidebar to render before the dish data resolves.
- `MenuSidebar` owns client state (expanded/collapsed links and toggle count). Navigate between `/menu` and `/menu/1` and return: the shared menu layout stays mounted, so the sidebar state is preserved.
- The dish list includes a short simulated delay so the Suspense fallback can be observed locally.

## Build verification

Run:

```bash
npm install
npm run build
```

The build output should mark `/menu` as static with a revalidation interval and list the dish detail routes generated by `generateStaticParams`. `/checkout` should be marked dynamic.
